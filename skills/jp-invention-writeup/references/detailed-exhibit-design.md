# 詳細実施例スライド（UIモック）の対話的構築ガイド

発明説明資料PPTXの実施例セクション（§4）で、**「実装が想像できるレベルの高品質UIモック」** を複数枚作るためのワークフロー。

単純な概念図（ボックスと矢印）では弁理士・審査官に「実装イメージ」が伝わらず、進歩性主張も弱い。**現実のWebアプリのスクショに見えるレベル** まで作り込むことで、請求項要素の具体化・実施可能性・差別化要素が一目で伝わる。

## このガイドの使い方

Claude がこのスキルで詳細実施例スライドを作るときは、**スライドごとに以下の質問テンプレートで発明者にヒアリングしてから HTML/CSS を書き出す**。ユーザに「全部一度に聞く」のではなく、3〜5問ずつに分けて対話する。

**ヒアリングは `AskUserQuestion` ツールで行う（SKILL.md「対話ルール」参照）。** 以下の質問テンプレートで `-`（ハイフン）で列挙している箇条書きは、そのまま **選択肢** として `AskUserQuestion` に渡す（例：Q-2 の画面種別・レイアウト比率、Q-4 のバッジ色分け、Q-7 のデザイントーンなど）。下のテンプレートは平文のプロンプト例だが、**実際の問いかけはこのツール経由で選択肢を出すこと。** 自由記述が必要な項目（Q-3 のエンティティ・属性、サンプルデータ等）はドラフト案を提示して修正を返してもらう形にする。1回のツール呼び出しは最大4問にまとめる。

## いつ詳細実施例スライドを作るか

以下のいずれかに当てはまる発明:
- 請求項対象がWebアプリ・業務ソフトウェア・データ可視化システム
- 進歩性のキーが「画面構成・UI上の操作・データ表現」にある
- 単純なフローチャートでは伝わらない複雑な相互作用がある

**目安**: 主要な実施例 3〜7枚（多すぎると説明会の時間オーバー、少なすぎると実装イメージが伝わらない）。

## 全体ステップ

1. **実施例スライド一覧を企画**（後述のQ-0）
2. **スライドごとに詳細ヒアリング**（後述のQ-1〜Q-7）
3. **デザインシステムを決定**（色・フォント・コンポーネント方針）
4. **HTML草案を作成 → PNG レンダ**
5. **ユーザレビュー → 修正の反復**
6. **吹き出し追加 → PPTXに埋込**
7. **品質チェックリスト確認**

## Q-0: 実施例スライド一覧の企画

最初にユーザに聞く：

```
詳細実施例スライドを作ります。以下を教えてください：

① 主要な機能領域はいくつありますか？（例：症例一覧／症例詳細／変化検知 など）
② 各機能領域で見せたい「ユーザのジャーニー」は？
   （例：症例詳細であれば「変異一覧 → 結論管理 → 家系図」のように画面遷移）
③ 各スライドが対応する請求項要素を1つ以上挙げてください
   （請求項に紐づかないスライドは作らない）
④ 想定する画面数（最小3、推奨5〜7、最大10）
```

回答を元に、以下のような企画表を作成しユーザに提示する:

| # | 機能領域 | サブ画面 | 対応請求項 |
|---|---|---|---|
| 1 | （データ）一覧 | リストビュー | 請求項1(独立項の蓄積・取得手段) |
| 2 | （データ）詳細 | 子要素一覧 | 請求項1(取得手段)＋ 請求項2(分類限定) |
| 3 | （データ）詳細 | 履歴・編集 | 請求項3(履歴管理) |
| ... | ... | ... | ... |

ユーザOKが出たらQ-1以降に進む。

## Q-1〜Q-7: スライド毎の詳細ヒアリング

各スライドについて、以下の7問を **一度に3〜5問ずつまとめて** 質問する。

### Q-1. このスライドが伝えたい主張は？

```
このスライド（{{機能領域}}：{{サブ画面}}）で：
（a）対応する請求項要素のうち、**特に強調したい1〜2要素** は？
（b）審査官／弁理士に「これは新規だ」と思わせる要素は何ですか？
（c）スライドのタイトルとサブタイトル案を1案ずつ
```

### Q-2. 画面の種別と主要レイアウト

```
画面の種別はどれが近いですか？
- 一覧画面（リスト・テーブル）
- 詳細画面（左に項目リスト＋右に詳細パネル）
- ダッシュボード（複数カード並列）
- 履歴・タイムライン
- 関係図（家系図・組織図・ネットワーク図）
- ウィザード（ステップフォーム）
- フローチャート
- その他（自由記述）

レイアウトの比率は？
- 左メイン65% + 右リスト35%
- 上部ヘッダ＋下部2カラム
- 上下に大きく2分割
- 単一カラム（縦長コンテンツ）
- その他
```

### Q-3. 画面に出てくるエンティティと属性

```
このスライドに出てくる主要なエンティティと属性を箇条書きしてください。

例:
- 症例（属性：ID, 氏名, 年齢, 性別, 疾患名, ステータス, 最終更新日）
- 変異（属性：遺伝子名, バリアント, VAF, ACMG分類, 推奨度）
- イベント（属性：日時, 種別, 担当者, コメント）

各属性の値の例（ダミーで構いません）も教えてください。リアル感が出るほど良い。
サンプル人名が必要な場合は「山田 花子」「山田 由美」等の中立な姓名を使います。
```

### Q-4. インタラクション要素（タブ・フィルタ・ボタン）

```
画面上で「ユーザが操作する」要素を教えてください。
- タブ: {{タブ名1, タブ名2, タブ名3}} （どれが active か？）
- 検索／フィルタ条件: {{条件キー1, 条件キー2}}
- ボタン: {{ボタンA, ボタンB}}
- ステータスバッジの色分け方針（例：緑=確定 / 黄=要対応 / 赤=重要）
- アイコン（任意）: ベル通知、設定歯車、ユーザアバター 等

「いま行われている操作」を視覚化したい場合、何の操作が active か？
（例：「タブ2が選択されていて変異一覧を表示中、その中で1行が選択されており詳細パネル展開中」）
```

### Q-5. 吹き出し（callout）で強調する要素

```
このスライドに付ける吹き出しは何個？（推奨 2〜4個。多すぎると視線が散る）

各吹き出しについて：
- 吹き出しのテキスト（30〜60字、「請求項Xの○○手段に対応」のような対応関係を含めると効果的）
- 吹き出しの指し先（anchor）は画面上のどの要素か（おおよその座標感覚で OK）
- 吹き出し本体の配置（画面の外側／余白に置く）
```

### Q-6. データの具体性

```
画面に表示するサンプルデータの粒度を決めます：
- 件数：表示する行数は？（多すぎると圧迫、少なすぎるとリアルじゃない、目安 5〜15行）
- 値の現実感：日付・数値・カテゴリ名は「業界の人が見て違和感ない」レベルにしますか？
  （ダミーでも整合性のある値を作る）
- 機微情報：実名・実患者名はNG。山田 花子等の中立名を使う
```

### Q-7. デザインの全体トーン

```
スライド全体のデザイン方向性：
- 主色（1スライドに1主色を選び、ヘッダ・タブactive・主要バッジに統一）
  - 青系 #1F6FEB（分析・データ系に多い）
  - 緑系 #10A37F or #2D6A4F（承認・同意系・ヘルスケア系）
  - 暖色 #D9534F（アラート・通知）
  - 紫系 #7C4DFF（推奨・マッチング）
  - ティール #0EA5A8（知識ベース・参照）
  - その他色を提案
- フォントウェイト：標準(400) / セミボールド(500) / ボールド(700) の組合せ
- 角丸・影：本物のアプリらしさを出すなら使う、線画寄りなら控える
- 余白：パネル間 16〜24px、内側パディング 16〜20px
```

## 反復ループ

### 第1イテレーション（草案）

1. Q-0〜Q-7 の回答を集約
2. `templates/ui-mockup.template.html` をベースに HTML を1枚作成
3. `render_html.js` で PNG 化
4. ユーザに PNG を見せて以下を確認:
   - レイアウトの大枠OK？
   - 主要属性が見えているか？
   - 主張したい要素が目立っているか？
   - 不要な要素はないか？

### 第2イテレーション（精緻化）

1. ユーザフィードバックを元に修正：典型的な修正点
   - 配置調整（パネル比、要素位置）
   - サンプルデータの追加・修正
   - バッジ色の見直し
   - 余白・タイポグラフィの調整
2. 再レンダ → 確認

### 第3イテレーション（吹き出し・最終調整）

1. 吹き出し（callout）を `add_image_with_bubbles()` で追加
2. PPTXに埋込
3. PowerPoint で実機確認

通常2〜3イテレーションで完成する。**1枚に時間をかけすぎず、5枚を粗く揃えてから全体を見直す方が品質が安定する**。

## 吹き出し（callout）の書き方

良い吹き出しの3要素:

1. **指し先が明確**: anchor 座標が画面上の具体的要素を指す
2. **テキストは「請求項要素 + 何をしているか」の2文構成**
   - 例：「請求項3（変化判定手段）に対応。過去結論と新エビデンスを比較し、LLMで要約コメントを自動生成する」
3. **30〜60字程度**: 長すぎると読まれない、短すぎると情報不足

避けるべきパターン:
- 画面要素そのままの説明（「ここに変異リストがある」）→ 画面を見れば分かる
- 抽象的すぎる主張（「ここが新規」）→ 何が新規か書く
- 4個以上の吹き出し → 視線が散る、要素を絞る

## 品質チェックリスト

完成前に以下を確認:

- [ ] 全スライドで主色が統一されている（バラバラの色を使わない）
- [ ] サンプル人名・データは中立（実名なし、業界違和感なし）
- [ ] 各スライドが少なくとも1つの請求項要素に紐づいている
- [ ] 吹き出しが2〜4個、テキストが30〜60字
- [ ] バッジの色割当（緑=確定／黄=要対応／赤=重要）が一貫
- [ ] 絵文字（👁📞📅🔬等）を使っていない（環境依存豆腐化リスク）
- [ ] 1920×1080 で完結（はみ出しなし、空白すぎる領域なし）
- [ ] 連続するスライドで同じ症例ID／ユーザIDを使い、ストーリーが追える
- [ ] Yu Gothic UI / Noto Sans JP が CSS で指定されている
- [ ] フッタに `識別子` `日付` `備考` などのメタ情報

## 過去案件の参考実装

具体的なHTML/CSS実装例として、過去案件（医療情報処理系・ヘルスケア系）で作成された7枚の詳細実施例HTMLが存在する場合は `~/patent/<過去案件>/work/figure-html-custom/exhibit-*.html` を参照すると、上記のデザインシステム・レイアウト・吹き出し設計の具体例が確認できる。

新規案件では、過去案件のHTMLを丸ごとコピーせず **構造とCSS変数定義のみを流用** し、コンテンツ（エンティティ名・タブ名・サンプルデータ）は新規案件のドメインに完全に置き換える。
