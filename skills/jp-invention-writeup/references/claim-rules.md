# 請求項の書き方ルール

JPO実務の請求項書式。組織内の過去サンプル `~/patent/sample/請求項.txt` があれば優先参照、なくとも以下のルールで動作する。

## 最重要：権利範囲の大原則（オールエレメント・ルール）

**請求項を書く前に必ずこの節を読む。書式より先に、権利の強さの原理を理解する。**

特許侵害は、原則として請求項の構成要素を **「全て」実施しているか** で判断される（オールエレメント・ルール）。したがって：

```
請求項 = 要素A & 要素B & 要素C & 要素D   ← 要素を足すほど権利範囲は狭く（弱く）なる
```

他社が「A & B & C（Dを含まない）」や「A & B & E & D（CをEに変えた）」を実施しても **侵害にならない**。要素を1つ足すたびに、その要素を持たない／別物に置き換えた実装はすべて権利範囲の外に出る。これは設計回避の口を自分で増やす行為に等しい。

**したがって独立項は、新規性・進歩性が保てる範囲で要素を「できるだけ書かない」のが正解。**

- 広い独立項で出願し、詳細は明細書に書いておく。
- 審査で「新規性・進歩性なし」と言われてから、明細書記載の範囲で要素を追加して限定していける（プロセキューション・ナローイング）。
- だから従属項は「審査で使う補正用の予備在庫」。最初から独立項に詰め込むと、この在庫を出願時点で使い切ってしまう。

### 「広さ」には独立な2軸がある（混同しないこと）

| 軸 | 望ましい方向 | 例 |
|---|---|---|
| **A. 分野（ドメイン）の広さ** | 案件方針に従う。**意図的に狭く限定してよい** | 「遺伝子変異の病的意義評価装置」に限定する／汎用エージェントに広げる |
| **B. 機構（構成要素）の広さ** | **常に広く。要素数・累積限定を最小化** | 手段の数、手段内の「〜の全て」「A かつ B」 |

ドメイン限定（A）は、そこに新規性が宿り、かつ出願人が守りたい範囲ならば狭めてよい（むしろ濃淡で言えば「濃＝残す」）。一方、機構の要素（B）を足すのは別の話で、これは権利を弱める。**「分野を絞りたい」という要望を、機構の要素を足す方向に誤って反映しない。** 分野はカテゴリ宣言（柱書）と各手段の目的語で限定し、機構は最小手段数に保つ。

### 着手前の濃淡整理（必須ステップ）

壁打ちで出たアイデアや差別化軸を、独立項に並べる前に必ず3段階に仕分ける：

| 濃淡 | 定義 | 行き先 |
|---|---|---|
| **核心** | これが無いと発明が成立しない／新規性の本質そのもの | 独立項（3〜5要素に収める） |
| **主要防御** | 進歩性主張の主軸。拒絶時に最初に取り込む候補 | 優先順位の高い従属項 |
| **任意限定** | あれば望ましい具体化・実施形態 | 在庫としての従属項 |

差別化軸が多い案件ほど、**それらを全部独立項に入れたくなる誘惑が強い**が、それは最悪手（＝独立項を最も狭くする）。差別化軸は基本「主要防御」以下に置き、独立項には核心だけを残す。

### 独立項のアンチパターン（このどれかに当てはまったら要修正）

- ❌ **手段（〜手段／〜工程）が多すぎる**。目安は **3〜5個**。6個以上は「核心」以外が紛れている疑い。
- ❌ **差別化軸を全部独立項に詰め込む**。「軸を盛り込む＝強い」は誤解。盛り込むほど狭い。
- ❌ **手段の内側の累積限定**：「(i)〜(v)の **全て**」「**少なくとも二以上**」「A **かつ** B の両方」。1つ足すごとに回避口が増える。独立項では「〜に基づき」程度の機能的記載に留め、列挙・必須個数は従属項へ。
- ❌ **具体名の独立項記載**：ベンダー名・特定アルゴリズム名・特定DB名・特定ガイドライン名（例：AMP/ASCO/CAP、BM25、特定製品）。独立項は機能的記載、具体名は従属項・実施例へ。
- ❌ **複数の独立した発明を1請求項に混在**。1請求項は1つの発明（単一性）。観点が違うものは別の独立項に分ける。

### 独立項を絞る手順

1. 「この要素を消したら、発明として成立しなくなるか？」を各要素に問う。成立するなら、その要素は独立項から外して従属項へ。
2. 複数の機能をまとめられる場合は、上位の機能的表現に束ねる（例：「発見手段＋構築手段＋検証手段＋蓄積手段」→「新たなスキルを獲得する獲得手段」。細目は従属項で分節化）。
3. 残った核心要素で、公知例との差別化が説明できるか確認する。説明できる最小集合が独立項。

## 全体構造

```
【請求項１（独立項のタイトル）】
(イ) 〜であって、
(ロ) 前記〜は、〜する第1手段と、
(ハ) 〜する第2手段と、
(ニ) 〜する第3手段を備えることを特徴とする。

===== (従属項) =====
【請求項２（従属項のタイトル）】
(ホ) 請求項１に記載の〜は、〜。

【請求項３（従属項のタイトル）】
(ヘ) 請求項２に記載の〜では、〜。
```

## ラベル順序（イロハ順）

`(イ) (ロ) (ハ) (ニ) (ホ) (ヘ) (ト) (チ) (リ) (ヌ) (ル) (ヲ) (ワ) (カ) (ヨ) (タ) (レ) (ソ) (ツ) (ネ) (ナ) (ラ) (ム)…`

- **独立項内で連番**、従属項では **独立項からの通し連番** で続ける
- 1案件に必ず1個ずつしか出ない（重複なし）
- サンプルでは独立項 (イ)(ロ)(ハ)(ニ)、従属項2 で (ホ)、従属項3 で (ヘ)、…と続く

## カテゴリ別の独立項テンプレ

### システム発明

```
【請求項１（〇〇の管理）】
(イ) 〇〇〇〇に関する情報を管理する情報処理システムであって、
(ロ) 前記情報処理システムは、〇〇〇〇する蓄積手段と、
(ハ) 〇〇〇〇する取得手段と、
(ニ) 前記取得手段により取得された〇〇〇〇を〇〇〇〇する表示手段を備えることを特徴とする。
```

### 方法発明

```
【請求項１（〇〇方法）】
(イ) コンピュータが実行する〇〇〇〇方法であって、
(ロ) 〇〇〇〇する工程と、
(ハ) 〇〇〇〇する工程と、
(ニ) 〇〇〇〇する工程を含むことを特徴とする。
```

### プログラム発明

```
【請求項１（〇〇プログラム）】
(イ) コンピュータに、
(ロ) 〇〇〇〇する処理と、
(ハ) 〇〇〇〇する処理と、
(ニ) 〇〇〇〇する処理を実行させるためのプログラム。
```

## 従属項の書き方パターン

### パターンA: 構成要素の限定

```
【請求項Ｎ（〇〇の限定）】
(X) 請求項１に記載の情報処理システムは、〇〇〇〇に基づいて〇〇〇〇を生成し、
```

### パターンB: 形式・形状の限定

```
【請求項Ｎ（表示形式の限定）】
(X) 請求項１に記載の〇〇では、〇〇〇〇形式を含み、〇〇〇〇可能であることを特徴とする。
```

### パターンC: 構成要素の追加

```
【請求項Ｎ（追加手段）】
(X) 請求項１に記載の情報処理システムは、〇〇〇〇する〇〇手段をさらに備え、
(Y) 前記〇〇手段は、〇〇〇〇を〇〇〇〇することを特徴とする。
```

### パターンD: アルゴリズム・処理の限定

```
【請求項Ｎ（要約生成方法の限定）】
(X) 請求項Ｍに記載の要約結果は、大規模言語モデルを用いて生成され、
(Y) 当該〇〇の〇〇を入力として、〇〇〇〇に基づき重み付けを行い要約結果を生成することを特徴とする。
```

## 推奨される従属項の数と観点

1案件あたり **5〜10項** が目安。以下の観点を網羅すると過不足が少ない：

| 観点 | 例 |
|---|---|
| 入力データの範囲限定 | 「外部データベースに蓄積された〜を含む」 |
| 表示方式の限定 | 「ロリポップ図状」「ポップアップ表示等」 |
| 処理アルゴリズムの限定 | 「大規模言語モデルを用いて」「重み付けを行い」 |
| 構成要素の追加 | 「〜手段をさらに備え」 |
| データ構造の限定 | 「テキスト情報として保持し」 |
| 利用者操作の限定 | 「ユーザの承認に基づき登録または更新」 |
| 方法・プログラムカテゴリ | システム発明と並行して同じ独立項を方法・プログラムで定義 |

## 重要な実務ノウハウ

1. **独立項は広く**：余計な限定要素を入れない。新規性が担保される最小限の要素（手段3〜5個）に絞る。理由と判定基準は冒頭「権利範囲の大原則（オールエレメント・ルール）」を参照
2. **従属項で深掘り**：差別化のキーとなる要素を別請求項として保護（＝拒絶時の補正用の予備在庫）
3. **「等」「その他」を活用**：列挙の末尾に付けて開示範囲を広げる
4. **「特徴とする」は独立項末尾と一部従属項にのみ**：すべての従属項に付ける必要はない（サンプル参照）
5. **公知例との差別化**：必ず公知例（`inputs/prior-art.txt`）と照合し、差別化要素が独立項に含まれているか確認

## 請求項の順序の決め方

請求項の並び順は **トピック集約順** が推奨。すなわち独立項の構成要素ごとに関連従属項を固める。
壁打ち時の発想順や戦略メモの優先度順では、後で読みづらく整理しにくい。

### 推奨パターン

1. **独立項** （請求項1）
2. **独立項の主要構成要素ごとに集約**
   - 候補抽出関連の限定 → 連番で続ける
   - 判定・提示関連の限定 → 連番で続ける
   - 拡張機能 → 連番で続ける
3. **横断的機能** （可視化／通知手段／UI要素）は末尾に

例（医療情報処理システム案件 — 9項。あくまで一例で、案件ごとに異なる）：
```
請求項1: 独立項
請求項2: 候補抽出の主要限定（スコアリングアルゴリズム）
請求項3: 候補抽出の代替パス（参照データの差し替え）
請求項4: 候補抽出の補強（追加検査・確認手順の推奨）
請求項5: 拡張機能（関係者展開、例：家族／取引先などへの波及）
請求項6: 拡張機能（権限・同意プロファイル — 請求項5に多重従属）
請求項7: 判定・提示の強化（LLMによる要約・コメント生成）
請求項8: UI（可視化）
請求項9: 配信（通知手段）
```

### 並び替えに伴うチェック項目

請求項を並び替える際は以下を一括更新する：
- **(イ)(ロ)(ハ) ラベル**: 全体で連番。並び替え後に各従属項のラベルが連続するよう振り直し
- **多重従属の参照**: 「請求項Ｎ又は請求項Ｍ」のNやMが移動先の番号に置き換わっているか
- **明細書中の請求項参照**: 「請求項4の判定手段」等の明細書本文／実施例説明での請求項番号
- **発明説明資料PPTXのサブタイトル**: 「（請求項Nに対応）」の番号
- **図面ファイル（特に画面例HTML）の請求項参照**

### やってはいけないこと

- ラベルの欠番（イ→ハ で ロ がない）
- 独立項より先に従属項を置く
- 後ろの請求項を前の請求項から参照する（「請求項５に記載の請求項３は…」のような循環）
- 多重従属の請求項を、その依存先より前に置く

## やってはいけないこと

- 独立項のタイトル `（〇〇〇）` を省略する（サンプルは全請求項に付いている）
- (イロハ)ラベルを欠番させる、または重複させる
- 独立項内に「前記」が無いまま参照する
- 末尾の「特徴とする。」を抜く
- 「特許請求の範囲」の見出しを忘れる（明細書統合時）
