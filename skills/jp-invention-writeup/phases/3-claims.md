# Phase 3: 請求項作成

独立項1つ＋従属項複数を、`references/claim-rules.md` の書式で作る。組織内の過去サンプル `~/patent/sample/請求項.txt` があればそれに寄せる。

> **最優先で読む**: `references/claim-rules.md` の「最重要：権利範囲の大原則（オールエレメント・ルール）」。
> 侵害は構成要素を **全て** 実施して初めて成立するため、**独立項に要素を足すほど権利は狭く弱くなる**。
> 独立項は新規性・進歩性を保てる **最小限の要素（手段3〜5個）** に絞り、差別化軸や詳細は従属項（＝補正用の予備在庫）へ落とす。
> 「分野（ドメイン）を絞りたい」という要望は柱書・目的語で限定することで満たし、**機構の要素を足す方向に誤変換しない**。

## 入力
- `~/patent/<案件名>/work/idea-expanded.md`
- `~/patent/<案件名>/inputs/prior-art.txt`（あれば）

## 出力
- `~/patent/<案件名>/output/請求項.txt`

## 書式ルール（サンプル準拠）

詳細は `references/claim-rules.md` を必ず参照する。エッセンスのみ再掲：

### 独立項

```
【請求項１（〇〇〇）】
(イ) ...〇〇システムであって、
(ロ) 前記〇〇システムは、〜する第1手段と、
(ハ) 〜する第2手段と、
(ニ) 〜する第3手段を備えることを特徴とする。
```

- タイトル `（〇〇〇）` は機能サマリ
- 各構成要素を **(イ)(ロ)(ハ)(ニ)(ホ)(ヘ)(ト)(チ)(リ)(ヌ)(ル)(ヲ)(ワ)(カ)(ヨ)(タ)…** で順番に振る
- 末尾は「〜を備えることを特徴とする。」または「〜を含むことを特徴とする。」

### 従属項

```
===== (従属項) =====
【請求項２（〇〇）】
(ホ) 請求項１に記載の〇〇システムは、〜する。

【請求項３（〇〇）】
(ヘ) 請求項２に記載の〇〇では、〜形式を含み、〜であることを特徴とする。
```

- 必ず `===== (従属項) =====` の区切り行を独立項と従属項の間に入れる
- 各従属項も `【請求項N（タイトル）】` で始め、(イロハ)ラベルは独立項からの連番

## 手順

### 0. 既存成果物の検出（差分作業モード判定）

着手前に以下を確認：
- `inputs/claims-draft.txt` があれば、**改訂モード** に切り替える：
  1. 既存ドラフトを読み、独立項・従属項の構造を把握
  2. `work/idea-expanded.md` の構成要素・実施形態と照合して **抜け** を特定
  3. `inputs/prior-art.txt` があれば、各公知例に対する差別化要素が独立項に含まれるか **チェック**
  4. 必要な改訂点（追加すべき従属項、独立項に追加すべき限定要素など）を **箇条書きで提案** してからユーザー承認を得る
  5. 承認後に `output/請求項.txt` を出力（既存ドラフトの文体・タイトル付け方を踏襲）
- `output/請求項.txt` が既にあれば、上書き前にユーザーに確認

新規の場合は手順1から始める。

### 0.5. 濃淡整理（独立項を書く前に必須）

`work/idea-expanded.md` のアイデア・差別化軸を、独立項に並べる前に必ず3段階に仕分け、ユーザーに表で見せて合意を取る。Claude の仕分け案を提示したうえで `AskUserQuestion` で「この仕分けで進む／入れ替えたい要素がある（自由入力）」を確認する：

| 濃淡 | 定義 | 行き先 |
|---|---|---|
| **核心** | 無いと発明が成立しない／新規性の本質 | 独立項（手段3〜5個に収める） |
| **主要防御** | 進歩性主張の主軸。拒絶時に最初に取り込む | 優先従属項 |
| **任意限定** | あれば望ましい具体化・実施形態 | 在庫としての従属項 |

差別化軸が多い案件ほど「全部独立項に入れたい」誘惑が強いが、それは独立項を最も狭くする最悪手。**差別化軸は原則「主要防御」以下に置く。** 詳細は `references/claim-rules.md` の同名節を参照。

### 1. 独立項の骨格を決める

「核心」に仕分けた要素 **だけ** で独立項を組み立てる。
構成要素は「〜手段」「〜部」の単位で分解（システムの場合）。方法発明なら「〜工程」。

骨格例：
- (イ) カテゴリ宣言: 「〇〇システムであって」（分野・ドメインの限定はここと各手段の目的語で行う）
- (ロ)〜: 各構成要素・手段（**3〜5個まで**。6個以上なら「核心」以外が紛れている）
- 末尾: 「〜を備えることを特徴とする。」

**独立項に書かないもの**（すべて従属項へ）：
- 手段内の累積限定（「(i)〜(v)の全て」「少なくとも二以上」「A かつ B の両方」）
- 具体名（ベンダー名・特定アルゴリズム名・特定DB名・特定ガイドライン名）
- 複数手段に分節できる細目（上位の機能的表現に束ね、分節化は従属項で行う）

### 2. 従属項を生成

`work/idea-expanded.md` の **「実施形態のバリエーション」** から従属項候補を抽出。
1案件あたり **5〜10項程度** が目安。観点別に整理：
- 入力データの限定（例：「外部DBに蓄積された情報を含む」）
- 表示形式の限定（例：「ロリポップ図状」）
- 処理アルゴリズムの限定（例：「大規模言語モデルを用いて」）
- 構成要素の追加（例：「〜手段をさらに備え」）

### 3. 公知例との差別化チェック

`inputs/prior-art.txt` の各文献に対し、独立項の (イ)(ロ)(ハ)... が **どの要素で差別化されているか** を表でユーザーに示す：

| 公知例 | 開示範囲 | 本発明の差別化要素 |
|---|---|---|
| 特許文献1 | 〜 | (ニ)の〇〇手段、(ホ)の〇〇 |

差別化要素が薄いと判断したら、独立項に限定要素を追加するかを `AskUserQuestion` で相談する（「限定要素を追加する＝差別化は強まるが権利は狭まる／追加せず従属項で備える」の2択。トレードオフを説明に明記）。

### 4. ファイル化

`templates/claims.template.txt` を雛型に、`output/請求項.txt` を書く。

### 5. ユーザーレビュー

請求項案をユーザーに見せ、以下を `AskUserQuestion` で確認（最後に「この内容で確定／修正する」を明示的に選ばせる）：
- 独立項の各要素は妥当か（過剰限定/過少限定）
- 従属項に抜けている観点はないか
- 用語は `work/idea-expanded.md` と整合しているか

**権利範囲チェック（オールエレメント・ルール観点。1つでも該当したら独立項を見直す）**：
- [ ] 独立項の手段は3〜5個に収まっているか（6個以上は要修正）
- [ ] 「この要素を消したら発明が成立しなくなるか？」を各要素に問い、成立するものは従属項へ落としたか
- [ ] 独立項に累積限定（「〜の全て」「少なくとも二以上」「A かつ B」）が紛れていないか
- [ ] 独立項に具体名（ベンダー／アルゴリズム／DB／ガイドライン名）が出ていないか
- [ ] 差別化軸を独立項に詰め込んでいないか（差別化軸は「主要防御」従属項に置く）
- [ ] 分野限定の要望を、機構の要素追加に誤変換していないか（分野は柱書・目的語で限定）
- [ ] 拒絶時に取り込む順（主要防御→任意限定）の予備在庫が従属項に残っているか
